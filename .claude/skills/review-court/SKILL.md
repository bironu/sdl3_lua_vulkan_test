# review-court

対象: `$ARGUMENTS`

引数に `--pre` が含まれていれば、手順 1.6 の Haiku 前処理を行う (対象のパスは `--pre` を除いた残り)。

## 手順

### 1. 対象の決定
- 引数が空: `git diff main...HEAD` と `git diff` (未コミット分) を合わせた変更を対象にする。差分が無ければユーザーに対象を聞く。
- 引数がパス: そのファイル/ディレクトリ全体。
- 引数がブランチ/PR 番号: `main` との差分。
変更ファイルの一覧 (`git diff --name-only`) を作る。`build/` `dist/` `res/` は除外する。

### 1.5 静的解析 (LLM を使わない。常に行う)
`python3 .claude/review/static-check.py <対象のパス>` を実行する (`build/compile_commands.json` が必要。無ければ `cmake -S . -B build` を先に)。
`clang++ -fsyntax-only` に警告 (`-Wall -Wextra -Wunused -Wshadow -Wunreachable-code` など) を足して、対象の警告を出す。この出力は手順 2・3 で、レビュアーと裁判官に「ヒント」として渡す (警告そのものは事実だが、直すかどうかは判決で決める)。

### 1.6 Haiku による前処理 (`--pre` のときだけ)
手順 1.5 の警告のうち、機械的に直せるものだけを `fixer-mechanical` (haiku) に直させ、レビューの前に入力を軽くする。
- **作業ブランチの確認**: `git branch --show-current` が `develop` `main` `master` なら、先に作業ブランチを切る。前処理の前に、未コミットの変更が無いか `git status` で確かめる (あればユーザーに知らせて止める)。
- 対象にしてよい警告: 未使用のローカル変数、未使用のラムダキャプチャ、未使用のプライベートフィールド、未使用のローカル型/マクロ。
- 対象にしない: 未使用の関数・メソッド・引数 (設計意図の可能性がある。判決で扱う)、shadow、到達不能コード、その他の警告。
- 直したあと、ビルド (`cmake --build build -j8`) を通す。通らなければ、その変更を `git checkout -- <ファイル>` で戻して、ユーザーに知らせる。
- 前処理の結果 (直した件数・戻した件数) をユーザーに示し、手順 2 に進む。コミットはしない。前処理で行番号が変わるので、手順 1.5 をもう一度回して、最新の警告をヒントにする。

### 2. レビュアーを並列起動
**1 つのメッセージで 4 つの Agent 呼び出しを同時に行う。** 範囲が広いとき (対象が合計 3000 行超、またはファイル 20 個超) は、コスト抑制のため、4 つの Agent 呼び出しに `model: "sonnet"` を指定する (judge は常に opus のまま)。範囲が広くてモデルを下げたことは、結果の冒頭でユーザーに伝える。各 subagent_type は:
- `reviewer-dedup`
- `reviewer-safety`
- `reviewer-complexity`
- `reviewer-perf`

各プロンプトに含めるもの: 対象ファイル一覧、手順 1.5 の静的解析の出力 (ヒントとして)、差分の取得方法 (`git diff` のコマンド)、「`.claude/review/project-notes.md` を最初に読むこと」、「指定の出力形式で返すこと」。
レビュアー同士の結果は互いに見せない (独立性を保つ)。
**範囲指定の規則**: 対象が複数のディレクトリにまたがる、または 1000 行を超えるときは、ディレクトリ (または責務) ごとに範囲を分け、各 reviewer に「対象ファイルの一覧」を明示し、「1 つずつ全部読むこと。読んでいないファイルは『未確認』と明記する」と指示する。範囲を指定しないと、reviewer は先頭付近のファイルしか見ない傾向がある (特に Sonnet)。返ってきた報告が、「読んだファイル」の範囲を示していない、または対象の一部しかカバーしていないときは、足りない範囲だけを再実行する。
報告は、judge に渡す前に、reviewer の出力ファイルから原文のままファイル (scratchpad) に抜き出してもよい (judge には、そのファイルのパスを渡して読ませる)。長い報告を、プロンプトに貼り直さずに済む。

### 3. 裁判官を起動
4 人の出力をそのまま (要約せず) `judge` に渡す。対象ファイル一覧、差分取得方法、手順 1.5 の静的解析の出力も添える。

### 4. 結果の提示
裁判官の判決をそのままユーザーに示す。続けて、
- 採用項目をまとめて修正するか、項目を選ぶかをユーザーに確認する。
- **ユーザーの承認なしにコードを変更しない。**

### 5. 修正の実施(承認された項目のみ)
ユーザーが承認した項目だけを、判決の「種別」に従って実装担当に渡す。
- **機械的** の項目 → `fixer-mechanical` (haiku)
- **要判断** の項目 → `fixer-careful` (sonnet)
- 渡すもの: 承認された項目 (`file:line`、問題、修正案) と、実施順序。保留・却下の項目は渡さない。
- 触るファイルが重ならなければ並列に起動してよい。重なる場合は直列にする (機械的 → 要判断の順)。
- 完了後、各 fixer の報告 (実施/未実施、ビルド結果) をユーザーに示す。未実施の項目は理由とともに知らせる。
- コミット・push はしない (ユーザーが頼んだときだけ)。頼まれてコミットするときは、先に `git branch --show-current` を確認し、`develop` `main` `master` 上なら作業ブランチを切ってからコミットする。

## モデル設定
モデルは各エージェントの frontmatter (`model:`) が既定。変更はそこだけ。
- `reviewer-*` と `judge`: `opus`
- `fixer-mechanical`: `haiku`
- `fixer-careful`: `sonnet`
- 範囲が広いときの reviewer は、手順 2 のとおり呼び出し時に `sonnet` へ切り替える (閾値は手順 2 の数字を直す)。

## 注意
- レビュアーが空 (指摘なし) でも裁判官は呼ぶ (棄却確認と総評のため)。
- 変更ファイルが非常に多い場合は、ディレクトリ単位に分割し、分割ごとにレビュアーを走らせて最後に裁判官 1 回で統合する。
